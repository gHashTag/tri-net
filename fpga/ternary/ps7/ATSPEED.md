# At speed, and where the silicon actually breaks

Every silicon result before this one was obtained by pushing one sample per
`devmem` write -- a few hundred samples a second. That proves arithmetic and
says nothing about throughput, and this project had never quoted a throughput
number. `ps7_speed.v` closes the gap: the 63-tap despreader is fed from a ROM in
the fabric, one sample per clock, and the comparison against the expected values
happens in the fabric too. The processor only starts the run and reads the
verdict.

## Result

```
done=1  errors=0  checked=256  cycles=258
=== VERDICT: 256 of 256 bit-exact, one sample per clock, 258 clocks ===
```

**256 samples consumed in 258 clocks, every output bit-identical to the software
reference.** One sample per clock, sustained, with no processor in the loop.

## The finding that took four runs to see

The first three attempts returned 256, then 240, then 186 errors. Two of those
were defects in the harness -- an off-by-one in the fabric comparator, and ROM
arrays declared as `wire` with `assign`, which never synthesised at all (the LUT
budget gave it away: 9746 against 9534 for the correlator alone, when two
256-entry ROMs should cost hundreds more). Both were mine, and both are fixed.

The third was not a defect at all:

```
FPGA0_CLK_CTRL = 0x00200500 -> IO PLL 1000 MHz / (5 x 2) = 100 MHz
kernel: /sys/kernel/debug/clk/fclk0/clk_rate = 99999999
nextpnr for this design: Max frequency 58.26 MHz
```

**The fabric was being clocked at 100 MHz while the design closes timing at
58 MHz.** A 1.7x overclock. Every design in this directory had been constrained
at 30.72 MHz -- a number chosen for the radio rate, not for the clock the PS
actually supplies. That was my error and it is worth stating plainly: constrain
at the clock you will *run*, then check what you will *feed*.

Lower FCLK below the closed frequency and the errors vanish:

```
FCLK 20 MHz : done=1 errors=0 checked=256 cycles=258
```

## Measured Fmax, on real silicon

With the design loaded once and only the PS clock divider changed between runs:

| FCLK | errors of 256 |
|---|---|
| 50.0 MHz | 0 |
| 55.6 MHz | 0 |
| 58.8 MHz | 0 |
| 62.5 MHz | 0 |
| 71.4 MHz | 0 |
| 76.9 MHz | 0 |
| **83.3 MHz** | **0** -- last clean point |
| **90.9 MHz** | **21** (repeat: 20) -- onset |
| 100.0 MHz | 181-190 |
| 50.0 MHz again | 0 -- fully reversible |

Three things worth taking from this table:

1. **Measured silicon Fmax is between 83.3 and 90.9 MHz.** nextpnr predicted
   58.26. The open flow's timing model is **conservative by roughly 1.5x** on
   this design -- wrong in the safe direction, which is the direction you want,
   but far enough off that quoting nextpnr's number as the achievable speed
   understates the part by half.
2. **The error count grows monotonically and reproducibly** (0, 21, 181), which
   is the signature of a setup violation across a distribution of path delays:
   the longest paths fail first. 90.9 MHz repeated at 20 and 21 errors.
3. **It recovers completely.** Returning to 50 MHz gives 0 errors again. This is
   a timing violation, not damage.

This is the first time this project has been able to say anything at all about
how fast its own logic runs on silicon, as opposed to what a tool estimated.

Logs: `results/speed7.log`, `results/sweep.log`, `results/sweep2.log`.

## Honest boundary

258 clocks for 256 samples is one sample per clock through a ROM, not through
the AD9361. At 83 MHz that is 83 Msample/s of correlator throughput, comfortably
above the 61.44 MSPS the radio would deliver -- but the radio is not connected to
it, and nothing here measures the datapath that would connect them.

## Place-and-route at image scale, and the end of the Docker dependency

The last open question was whether nextpnr can place and route a design the size
of the full image -- `axi_ad9361` 7 447 LUT + `axi_dmac` 725 + our correlator
9 534 = 17 706 -- on this chipdb, in what runtime, and at what clock. Other
projects report runs of hours or overnight, and one known failure mode is
strict legalisation of distributed RAM.

### The toolchain is now local

`nix` was already installed on this machine, and nixpkgs publishes a **prebuilt
`nextpnr-xilinx` for aarch64-darwin**. Fetched from the binary cache -- no
source build, no 11 GB container:

```
/nix/store/8jqjlvwiffwlgqrigh4fgvji87fpmri4-nextpnr-xilinx-0.8.2-unstable-2026-03-13
nextpnr-xilinx -- Next Generation Place and Route (Version 96bb068)
```

**The chipdb generated by the container's nextpnr loads in this one without
complaint.** There is no version gate in the loader, and the constid-count
assertion that would catch a mismatch did not fire. `ps7_corr` places and routes
to `113.26 MHz`, against `115.00 MHz` from the container -- same design, two
different nextpnr builds, a 1.5% difference.

So the flow is yosys 0.67 + nextpnr-xilinx from nix + the saved chipdb, entirely
local. **Docker is no longer required for anything.**

### The scaling answer

`ps7_scale` -- two 63-tap despreaders side by side, 12 773 LUT synthesised,
**18 999 SLICE_LUTX placed**, 72% of the full image's LUT count:

```
exit 0          wall clock: 62 s
router: 11 iterations, 432 394 wires, overused -> 0, archfail 0
Max frequency for clock 'FCLKCLK[0]': 51.41 MHz (PASS at 30.72 MHz)
SLICE_LUTX 18 999/106 400 (17%)   SLICE_FFX 2 366   CARRY4 768
```

| design | LUT | placed SLICE_LUTX | Fmax | runtime |
|---|---|---|---|---|
| one 63-tap despreader | 9 534 | -- | 58.36 MHz | seconds |
| two, side by side | 12 773 | **18 999** | **51.41 MHz** | **62 s** |

**Sixty-two seconds, not hours.** The router converged cleanly. Fmax fell 12%
for a 49% larger placed design -- graceful, not a cliff.

### What is now known, and what is not

Known: the flow builds locally, the chipdb is portable across nextpnr builds,
and a design at image scale places and routes in about a minute with room to
spare on the device.

Not known: this is our own logic, which is regular and carry-chain-heavy.
`axi_ad9361` is AXI-heavy control logic with a different routing profile, and it
has not been placed. The 12% Fmax cost of doubling may not be the cost of adding
a different *kind* of logic. And every Fmax here is still nextpnr's own estimate
on a model with **no sequential timing component at all** -- the silicon sweep
in this file measured 83-91 MHz where the tool predicted 58.

Log: `results/pnr_scale_2x63tap.log`.

## The whole flow, validated on silicon

A bitstream built with **no vendor tool and no container anywhere in the chain**
was loaded into the PL and verified:

```
state: operating
EMIO : 0x000047C0            <- our anchor; our design is in the fabric
=== VERDICT: 256 of 256 bit-exact against the software reference ===
EXIT=0
```

The chain: **yosys 0.67** (Homebrew) -> **nextpnr-xilinx 96bb068**, built from
source here with the DSP FASM fix -> **fasm2frames** (prjxray's own, on the
Python library) -> **xc7frames2bit**, built from source here. All on
aarch64-darwin, none of it available prebuilt for this platform.

That is the toolchain question answered from both ends: it builds, and what it
builds runs.

### And the AD9361 bitstream was verified without touching the board

`axi_ad9361`'s bitstream exists and round-trips cleanly:

```
fed in    : 7 802 frames, 101 words each
read back : 9 996 frames (the extra 2 194 are padding)
addresses in both      : 7 802
in both, data differs  : 0
non-zero frames fed in : 5 544, all identical on read-back
```

**It was not loaded, and that is deliberate.** Every previous load in this
project was safe for a reason `FIRST_LOAD.md` states plainly: those designs
"declare no ports at all ... cannot drive a board pin and cannot conflict with
the AD9361 front end." The AD9361 harness is the opposite -- 30 real package
pins, **16 of them outputs**, assigned arbitrarily from banks 34 and 35 rather
than from this board's schematic. If any lands on a pin something else drives,
that is contention on real hardware.

So it was verified by construction instead: `bitread` extracts the frames back
out and every one matches what went in. That proves the bitstream encodes the
intended configuration. It does not prove the pinout is safe for this board,
and nothing short of the schematic would.

Log: `results/newflow_silicon.log`.
